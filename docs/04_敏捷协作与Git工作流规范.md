### 一、敏捷协作机制

#### 1.1 迭代节奏

每个 Sprint 为 2 周，按 Sprint 1 → 2 → 3 推进，交付范围与 `docs/01` 需求基线一致：

| 迭代 | 交付范围 | 版本标签 |
| :---: | :--- | :--- |
| Sprint 1 | US-01 ~ US-08（认证 / 商品 / 砍价 / 门户 / 工程脚本，29 SP） | `v1.0.0` |
| Sprint 2 | US-09、US-10（留言互动 / 意向预约，10 SP） | `v1.1.0` |
| Sprint 3 | US-11、US-12（信用评价与举报 / 管理后台，13 SP） | `v1.2.0` |

#### 1.2 敏捷会议

| 活动 | 频次 / 时间 | 参与人 | 输出 |
| :--- | :--- | :--- | :--- |
| Sprint 计划会 | 迭代首日 30 分钟 | 全员 | Sprint Backlog（卡片认领到人） |
| 每日站会 | 每日 15 分钟 | 全员 | 昨日完成 / 今日计划 / 当前阻塞 |
| 迭代评审会 | 迭代末日 45 分钟 | 全员 + 组外评审 | 可运行增量演示 + AC 验收结果 |
| 迭代回顾会 | 评审会后 30 分钟 | 全员 | 改进项清单（下个迭代跟踪） |

#### 1.3 看板与卡片规范

1. 迭代看板设 6 个列表：**Backlog → To Do → In Progress → Review → Test → Done**；
2. 卡片标题格式：`[US-xx] 子任务描述`；描述中必须链接对应 AC（如 AC-6.4）；卡片指定负责人并配置子任务勾选清单；
3. 卡片流转即状态：开发完成 → `Review`（代码评审）→ `Test`（回归验证）→ `Done`（满足 DoD）；
4. 燃尽图由宋杰每迭代维护，卡片与子任务状态同步更新。

#### 1.4 变更管理（契约先行）

| 变更类型 | 流程 |
| :--- | :--- |
| 需求变更 | 站会提出 → 边皓东评估 → 更新 `docs/01` 需求基线 → 同步 `docs/05` 分工表 |
| 接口变更 | **先更新 `docs/02` API 契约** → 受影响模块主责人在站会同步 → 再修改代码 |
| 表结构变更 | 更新 `docs/03` 数据字典与 DDL → 同步 `db/init.sql` → 全组重建数据库验证 |

### 二、Git 分支模型（简化 Git Flow）

#### 2.1 分支定义

| 分支 | 来源 | 去向 | 用途 |
| :--- | :--- | :--- | :--- |
| `main` | — | — | 可交付稳定版；仅接受 `release/` 与 `hotfix/` 合入；每次合入打版本标签 |
| `develop` | `main` | `release/` | 日常集成主干，所有功能分支在此汇合 |
| `feature/<us>-<desc>` | `develop` | `develop` | 单个用户故事 / 子模块开发 |
| `release/v<版本>` | `develop` | `main` + `develop` | 迭代发布准备与验收期缺陷修复 |
| `hotfix/<desc>` | `main` | `main` + `develop` | 交付后紧急缺陷修复 |

#### 2.2 命名与生命周期规则

1. 分支命名全小写，用 `-` 连接：`feature/us-06-bargain`、`feature/us-10-reservation`、`hotfix/fix-login-4002`；
2. `main` 与 `develop` 开启保护：禁止直接推送，只能通过 Pull Request 合入；
3. feature 分支生命周期不超过 3 天，跨天未合并需在站会说明进度；
4. 合并完成后删除源分支，保持仓库分支列表整洁。

### 三、提交规范（Conventional Commits）

#### 3.1 格式

```text
<type>(<scope>): <subject>

[可选正文：说明变更原因与影响面]
```

#### 3.2 type 取值

| type | 含义 |
| :--- | :--- |
| feat | 新功能 |
| fix | 缺陷修复 |
| refactor | 重构（不改变外部行为） |
| docs | 文档变更 |
| test | 测试相关 |
| style | 格式调整（不影响逻辑） |
| chore | 构建 / 依赖 / 杂项 |

#### 3.3 scope 取值

`auth` / `item` / `image` / `message` / `bargain` / `reserve` / `review` / `report` / `admin` / `ui` / `db` / `docs` / `deploy` / `test`

#### 3.4 提交示例

```text
feat(auth): 实现学号注册与 JWT 签发 (US-01)
feat(bargain): 接受出价后联动商品置为已售 (AC-6.4)
fix(item): 修正下架商品仍出现在集市列表 (AC-5.3)
docs(db): 补充预约表索引与状态说明 (US-10)
test(api): 新增留言断言组 (AC-9.x)
```

#### 3.5 规则

1. 提交标题一行不超过 72 字符；正文说明「为什么」，可写明关联 US / AC 编号；
2. 一个提交只做一件事，禁止混合提交（如同时改表单与数据库脚本）；
3. 禁止提交本地配置、密码明文、构建产物临时文件等无关内容。

### 四、合并与代码评审

#### 4.1 Pull Request 流程

1. feature 分支开发完成：后端跑通 `mvn test`；接口改动执行 Apifox 集合（`tests/apifox`）或 `tests/api-e2e.ps1` 对应断言组；前端改动执行 `cd frontend && npm test`（Playwright）；
2. 向 `develop` 发起 Pull Request，按模板填写：**关联 US / AC、变更内容、自测方式、UI 截图（涉及页面时）**；
3. 至少 1 名成员 Review 通过（前端 ↔ 后端交叉评审：接口改动必须由对端负责人确认契约一致）；
4. 使用 Squash Merge 合入 `develop`，删除源分支。

#### 4.2 Review 检查清单

- 对应 AC 是否全部覆盖，边界情况是否处理；
- 错误码是否符合 `docs/02` 契约（4001 ~ 4007）；
- 越权校验是否实现（他人商品、非管理员、非交易参与方）；
- SQL 是否走到 `docs/03` 设计的索引，是否存在 N+1 查询；
- 前端交互：空状态、加载态、移动端适配、复制提示等是否完整。

### 五、质量门禁与版本管理

#### 5.1 合并门禁（必须全部满足）

1. `mvn test` 通过（40 项 JUnit 5 + Mockito：启动冒烟 + 核心业务规则）；
2. 涉及接口的改动：Apifox 全量集合（96 请求 / 117 断言）或 `tests/api-e2e.ps1`（62 项断言）对应断言通过（用例清单见 `docs/06`）；
3. 涉及页面的改动：`cd frontend && npm test`（Playwright 关键流程）通过；
4. 受影响文档（`docs/01 ~ 06`）同步更新。

#### 5.2 迭代发布流程

1. 迭代末从 `develop` 创建 `release/v<版本>`，冻结功能，只修缺陷；
2. 伍宇轩在 release 分支执行全量 E2E 回归，边皓东对照 `docs/01` 完成 AC 验收；
3. 验收通过后合入 `main` 并打标签（`v1.0.0` / `v1.1.0` / `v1.2.0`），随后反向合回 `develop`；
4. 发布包由 `一键启动.bat` 全自动构建与启动（US-07 验收路径）。

#### 完成定义（Definition of Done）

一个卡片满足以下全部条件才可移入 Done：

1. 代码实现完成，对应 AC 自测通过；
2. `tests/api-e2e.ps1` 相关断言组通过；
3. 受影响文档同步更新（含接口契约与数据字典）；
4. Review 通过并合入 `develop`。
